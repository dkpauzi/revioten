## 2. Cara mengulang dari nol (Windows)

Dari root repo, di PowerShell. Semua perintah di bawah belum dicoba di komputer pemilik.

1. `git pull`, lalu `docker compose up -d`.
2. `go test ./...` (Docker harus berjalan), lalu `npm --prefix web test` dan `npm --prefix web run check`.
3. `npm --prefix web run build`, lalu `go run ./cmd/revioten`. Migrasi `00006_create_processes.sql` berjalan sendiri.
4. Login dengan akun admin. Buka Accounts, lalu buat akun kerja untuk PPAP Engineer dengan peran "Template maintainer". Catat password sementaranya.
5. Masih dengan akun admin, buka Processes: daftar terlihat, tapi tanpa formulir. Akun admin tidak memegang E-6 (D-64).
6. Logout, lalu login dengan akun PPAP Engineer dan ganti password.
7. Di Processes, tambah "Parts Receiving" dengan alias "Part Receiving". Lalu coba tambah "IQC" dengan alias "parts receiving": ditolak, karena nama itu sudah dipakai.
8. Tekan "Edit" pada "Parts Receiving", ganti nama menjadi "Receiving", lalu "Save".
9. Logout, login dengan akun admin, dan buka Audit log. Entri "Process added" dan "Process changed" sama-sama menampilkan sasaran "Receiving", karena keduanya menunjuk ID yang sama.
10. Test E2E: `npm --prefix web run test:e2e`.

## 4. Konsep yang dipelajari

**Nama sebagai tampilan, ID sebagai identitas.** Tabel `processes` hanya berisi `id` dan `created_at`. Semua nama ada di tabel `process_names`. Mengganti nama hanya mengubah satu baris di `process_names`, sedangkan data lain menunjuk `processes.id` dengan foreign key. Baris dokumen belum ada (Tahap 3), jadi `TestRenameKeepsReferences` membuat tabel tiruan `test_rows` yang menunjuk proses. Setelah nama diganti, baris tiruan itu langsung menampilkan nama baru, dan proses yang dirujuk tidak bisa dihapus (foreign key menolak, kode 23503).

**Satu ruang nama dengan kolom hasil hitung.** Kolom `name_key` didefinisikan `GENERATED ALWAYS AS (lower(name)) STORED`: database menghitungnya sendiri dari `name`, dan aplikasi tidak bisa mengisinya. Kolom ini menjadi primary key, jadi "IQC" dan "iqc" dianggap nama yang sama, baik sebagai nama tampilan maupun alias. Aturannya ada di database, bukan hanya di kode Go.

**Urutan langkah dalam satu transaksi.** Untuk menukar nama dan alias ("IQC" dengan alias "Incoming QC" menjadi "Incoming QC" dengan alias "IQC"), `Update` melepas alias lama dulu, baru mengganti nama tampilan, lalu memasang alias baru. Dengan urutan lain, primary key menolak karena nama baru masih dipakai alias lama.

**Kunci baris agar perubahan bergantian.** `Update` mengunci baris nama tampilan dengan `FOR UPDATE` sebelum membaca nilai lama. Tanpa kunci, dua perubahan paralel membaca nilai lama yang sama, dan alias bisa menjadi gabungan keduanya (lihat uji mutasi). Yang dikunci adalah baris `process_names`, bukan `processes`, karena dua alasan:
- mengunci baris butuh hak `UPDATE`, sedangkan role aplikasi sengaja tidak punya `UPDATE` di `processes` (dibuktikan: `SELECT ... FOR NO KEY UPDATE` ditolak);
- baris `processes` nanti dirujuk baris dokumen lewat foreign key. Kunci di sana tidak perlu ikut menunggu (pelajaran deadlock M1.3).

**Penolakan database diterjemahkan menjadi pesan per field.** Bila primary key menolak, layanan tahu langkah mana yang gagal: nama tampilan (`name:taken`) atau alias (`aliases:taken`). `TestCreateConcurrent` menjalankan 10 pendaftaran paralel dengan nama yang sama: tepat satu berhasil, dan sembilan lainnya mendapat `name:taken`, bukan error server.

**Daftar kosong berbeda dengan tidak dikirim.** Di JSON, `"aliases": []` menjadi daftar kosong di Go, sedangkan field yang tidak dikirim menjadi `nil`. `PUT /api/v1/processes/{id}` menolak permintaan tanpa `aliases`, karena isinya menggantikan semua alias (E-34).

**Tabel izin dengan tiga pelaku.** Tabel `TestPermissionsPerOperation` kini memeriksa setiap operasi untuk Viewer, PPAP Engineer, dan admin. Master proses adalah master pertama yang tidak bisa diubah admin: admin mendapat 403, dan hanya pemegang E-6 yang mendapat 201 atau 200 (D-64, D-72).

## 5. Keputusan beserta alasannya

1. **Satu master proses untuk semua customer** (ASUMSI E-32). Template per customer menyusul di M3.2 (R-TPL-03), tapi proses dasarnya sama, sehingga pencocokan lintas dokumen memakai satu daftar ID.
2. **Nama dan alias berbagi satu ruang nama**, tanpa membedakan huruf besar kecil, dan spasi ganda di tengah nama dirapikan menjadi satu (ASUMSI E-32). Dengan begitu satu nama selalu menunjuk paling banyak satu proses, termasuk saat impor nanti (R-DOC-04).
3. **Nama lama tidak otomatis menjadi alias.** Ganti nama sering untuk membetulkan salah ketik. Bila nama lama perlu tetap dikenali, PPAP Engineer menambahkannya sebagai alias dalam perubahan yang sama.
4. **Alias diganti sekaligus** lewat `PUT` dengan daftar lengkap, sama seperti peran akun di M1.2. Alias boleh dihapus dari database karena tidak ada data yang menunjuknya; proses tidak pernah dihapus.
5. **Belum ada status nonaktif untuk proses**, sama seperti group model dan model di M1.4 (E-30). Status ini ditambah saat Tahap 3 butuh daftar pilihan proses.
6. **Sub-proses belum dibuat** (ASUMSI E-33). R-TPL-01 menaruhnya di process template (M3.2). Tingkat pencocokan dokumen (proses atau sub-proses) dicatat sebagai temuan E-33.
7. **Ada endpoint satu proses menurut ID** (`GET /api/v1/processes/{processId}`). Endpoint ini membuktikan kriteria selesai di tingkat API: pemanggil yang menyimpan ID tetap mendapat proses yang sama setelah nama diganti.

## 7. Temuan desain

- **E-32 (baru, Terbuka):** aturan nama dan alias master proses belum ditetapkan.
- **E-33 (baru, Terbuka):** belum jelas apakah PFD, PFMEA, dan CP dicocokkan di tingkat proses atau sub-proses. Perlu diputuskan sebelum M3.2.
- **E-34 (baru, Terbuka):** kode hasil generate tidak memeriksa field wajib di kontrak. Contoh yang sudah ada: `PUT /api/v1/customers/{id}` tanpa `active` menonaktifkan customer. Belum diubah, supaya M1.5 tidak melebar ke M1.4.
- **Catatan untuk M1.8:** `Authorize` meloloskan hak bercakupan Project Group bila operasinya tidak menyebut customer. Saat ini aman, karena hanya Penyusun dan Verifikator yang bisa bercakupan Project Group dan master proses memakai E-6 (selalu semua customer). Ini diperiksa lagi saat cakupan Project Group diaktifkan di M1.8.
