## 2. Cara mengulang dari nol (Windows)

Dari root repo, di PowerShell. Semua perintah di bawah belum dicoba di komputer pemilik.

1. `git pull`, lalu `docker compose up -d`.
2. `go test ./...` (Docker harus berjalan), lalu `npm --prefix web ci`, `npm --prefix web test`, dan `npm --prefix web run check`.
3. Buat akun admin pertama:
   - jalankan `go run ./cmd/revioten create-admin -name "Nama Anda" -login admin.anda`;
   - ketik password dua kali, minimal 15 karakter. Password tidak tampil di layar;
   - jalankan perintah yang sama sekali lagi: hasilnya "akun admin sudah ada".
4. Coba sendiri:
   - `npm --prefix web run build`, lalu `go run ./cmd/revioten`;
   - buka http://127.0.0.1:8080/customers. Browser diarahkan ke `/login?next=%2Fcustomers`;
   - login, lalu Anda kembali ke daftar customer;
   - coba password salah, tombol "Log out", dan halaman "Change password".
5. Test E2E: `npm --prefix web run test:e2e`. Skrip membuat akun admin uji sendiri di database `revioten_e2e`.
6. Bila browser tidak menyimpan cookie (tetap kembali ke halaman login setelah login berhasil), catat browser dan versinya. Cookie memakai atribut `Secure`, yang diterima Chrome, Edge, dan Firefox di `localhost` dan `127.0.0.1`.

## 4. Konsep yang dipelajari

**Hash password dengan argon2id.** Password tidak pernah disimpan, hanya hash-nya. argon2id sengaja lambat dan memakan memori (19 MiB per percobaan), sehingga menebak jutaan password dari database yang bocor menjadi mahal. Salt acak membuat dua orang dengan password yang sama punya hash berbeda. Format PHC (`$argon2id$v=19$m=19456,t=2,p=1$salt$hash`) menyimpan parameternya, jadi hash lama tetap bisa diperiksa setelah parameter dinaikkan. Dalam keadaan itu, `verifyPassword` melaporkan `needsRehash`, dan hash dibuat ulang saat login berikutnya.

**Membandingkan dengan waktu tetap.** `subtle.ConstantTimeCompare` butuh waktu yang sama walau byte pertama sudah beda. Untuk nama login yang tidak ada pun hash tetap dihitung (`dummyHash`). Dengan begitu lama jawaban tidak membocorkan apakah sebuah nama login terdaftar.

**Sesi di database, token di cookie.** Token sesi berisi 256 bit acak. Browser menyimpan token di cookie, sedangkan database hanya menyimpan SHA-256-nya. Bila isi database bocor, tidak ada sesi yang bisa dipakai. Untuk token cukup SHA-256, karena token acak tidak bisa ditebak dari kamus seperti password. Logout menghapus baris sesi, jadi token lama langsung tidak berlaku.

**Atribut cookie.**
- `HttpOnly`: JavaScript tidak bisa membaca cookie, sehingga celah XSS tidak bisa mencuri sesi.
- `Secure` dan awalan `__Host-`: cookie hanya dikirim lewat koneksi aman (browser menganggap localhost aman), dan tidak bisa dipasang subdomain lain.
- `SameSite=Lax`: browser tidak mengirim cookie pada POST dari situs lain.

**CSRF dan cek Origin.** Browser mengirim cookie otomatis, jadi situs jahat bisa mencoba membuat browser pengguna mengirim POST ke sistem ini. `http.CrossOriginProtection` (pustaka standar Go sejak 1.25) membaca header `Sec-Fetch-Site` dan `Origin` yang dipasang browser, lalu menolak POST, PUT, PATCH, dan DELETE dari situs lain. Permintaan tanpa kedua header (misalnya curl) dibiarkan, karena CSRF hanya terjadi lewat browser.

**Middleware dan "tolak bila tidak disebut".** `requireSession` dipasang di semua route API. Hanya route di `publicRoutes` yang lolos tanpa sesi, jadi endpoint baru yang lupa didaftarkan otomatis terkunci. Middleware ini berjalan setelah ServeMux memilih route, sehingga `r.Pattern` (Go 1.23+) berisi pola route seperti `GET /api/v1/customers`. `TestPublicRoutesMatchContract` membaca `api/openapi.yaml` dan memastikan daftar itu sama dengan operasi bertanda `security: []`.

**Penjaga halaman.** Halaman SPA tidak berisi data, tapi milestone meminta halaman tanpa login ditolak. Server mengarahkan permintaan halaman tanpa sesi ke `/login?next=...` (303 See Other). Di browser, layout memeriksa `GET /api/v1/session`, dan setiap jawaban 401 dari API membawa ke halaman login. Parameter `next` diperiksa `safeNext`, supaya tautan palsu tidak bisa membawa pengguna ke situs lain setelah login (open redirect).

**Kunci advisory PostgreSQL.** `pg_advisory_xact_lock(n)` memegang kunci bernomor sampai transaksi selesai. Dua perintah `create-admin` yang berjalan bersamaan tidak bisa sama-sama lolos cek "belum ada admin". `TestCreateFirstAdminConcurrent` menjalankan 10 perintah sekaligus, dan hasilnya tepat satu admin. Konsep ini dipakai lagi untuk penomoran (M2.2).

**Jam palsu di test.** `Service.now` bisa diganti. Test memajukan jam 30 menit atau 8 jam tanpa menunggu, untuk membuktikan batas tidak aktif, batas mutlak, dan lama kunci akun.

## 5. Keputusan beserta alasannya

1. **Nilai aturan login dari standar** (ASUMSI E-08, tabel lengkap di `docs/evaluasi-desain.md`, E-08 bagian Pelaksanaan). Teks OWASP, ASVS 5.0, dan NIST SP 800-63B-4 dibaca dari repo resminya di GitHub, karena situsnya tidak dibuka dari cloud.
2. **Password minimal 15 karakter.** Login hanya memakai password (satu faktor), dan NIST mewajibkan 15 untuk keadaan itu. Petunjuk di layar menyarankan beberapa kata dengan spasi.
3. **Akun admin pertama lewat CLI dengan pipa atau terminal.** Password tidak bisa diberikan lewat flag, supaya tidak tersimpan di riwayat perintah.
4. **Daftar route publik di kode, dicek terhadap kontrak.** oapi-codegen v2.8.1 tidak lagi membuat penanda keamanan di context (sudah usang). Pengganti resminya, middleware validasi berbasis kin-openapi, dinilai terlalu berat untuk proyek ini.
5. **`internal/problem` dibuat sekarang**, karena customer dan auth butuh bentuk penolakan yang sama, dan master data di M1.4 sampai M1.8 akan memakainya juga.
6. **`SameSite=Lax`, bukan `Strict`.** Dengan `Strict`, tautan ke sistem ini dari email atau dokumen lain selalu mendarat di halaman login dulu. Perlindungan CSRF utamanya sudah dari cek Origin.
7. **Selama wajib ganti password**, akun hanya boleh melihat sesi, logout, dan ganti password (403 `password_change_required`). Saat ini belum ada cara memasang tanda itu (reset oleh admin datang di M1.2), tapi jalurnya sudah dites.
8. **Nama login dan peristiwa keamanan dicatat di log server** (login gagal, akun dikunci, akun dinonaktifkan, admin pertama dibuat). Mulai M1.3 peristiwa ini juga masuk audit log.

- **E-22 (baru, Terbuka):** tidak ada jalan keluar bila akun admin terakhir lupa password atau dinonaktifkan setelah 100 kali gagal. Kunci akun juga bisa dipakai pihak luar untuk mengunci admin.
