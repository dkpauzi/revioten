# M1.7 · Backup data lokal

- **Tanggal:** 30 Oktober 2026
- **Dasar:** milestone M1.7 (Tambah usulan), dibangun sebelum M2.1 atas persetujuan pemilik 30 Oktober 2026 (D-119, rekomendasi bagian 5 lembar evaluasi Tahap 1). Rujukan lain: D-29, D-36, R-SEC-03 (jangkar luar rantai audit), R-SEC-04, RK-23, RK-49, E-29.
- **Selesai bila (milestone):** restore berhasil dan langkahnya tertulis. Tercapai: uji restore otomatis (`TestBackupAndRestore`) dan manual lewat Docker Compose (bagian 3).

## 1. Tujuan dan apa yang dibuat

Data asli dipakai di localhost sejak awal (D-29, D-36), dan mulai Tahap 2 register nomor terisi. Nomor tidak pernah dipakai ulang, jadi kehilangan register adalah kerugian yang paling mahal. M1.7 menyiapkan backup terenkripsi dan membuktikan bahwa backup itu bisa dipulihkan.

Yang dibuat:
- **`revioten backup`** (`cmd/revioten/backup.go`): `pg_dump` (format custom) dijalankan di container `db` lewat `docker compose exec -T`, hasilnya langsung dienkripsi dengan age memakai passphrase, lalu ditulis ke `BACKUP_DIR`. File sementara diganti nama setelah lengkap, jadi tidak ada backup setengah jadi.
- **Manifest** di samping setiap backup (`revioten-<waktu>.manifest.json`): ukuran dan SHA-256 file terenkripsi, versi skema (migrasi terakhir), dan ujung rantai audit (nomor dan hash entri terakhir). Ujung rantai yang tersimpan di luar database adalah jangkar luar R-SEC-03: penulisan ulang seluruh rantai oleh admin database tetap ketahuan dari manifest lama.
- **`revioten restore -file <backup> [-db nama]`**: hash file dicocokkan dengan manifest, passphrase diperiksa, database **baru** dibuat (database yang sudah ada tidak pernah ditimpa), role `revioten_app` disiapkan bila belum ada, isinya dipulihkan dengan `pg_restore --single-transaction`, lalu rantai audit database baru diperiksa dan ujungnya dicocokkan dengan manifest. Bila pemulihan gagal, database yang baru dibuat dibuang lagi.
- **Paket `internal/backup`**: enkripsi, manifest, pemeriksaan file, dan alur restore. Paket ini tidak menjalankan `pg_dump` sendiri; perintah CLI memakai Docker Compose, test memakai container test.
- **`audit.VerifyChain`, `audit.ChainHead`, `audit.HashAt`**: pemeriksaan rantai tanpa pemeriksaan izin, khusus untuk perintah di komputer server (seperti `create-admin`). Layar dan API tetap lewat `Service.Verify` dengan hak A-4.
- **`db.SchemaVersion`, `db.EnsureAppRole`**, pengaturan `BACKUP_DIR` dan `BACKUP_PASSPHRASE` di `.env.example`, dan dependensi baru `filippo.io/age` v1.3.2 (`docs/versions.md`).

## 2. Cara mengulang dari nol (Windows)

Belum dicoba di komputer pemilik.

1. Siapkan folder di disk lain, misalnya disk eksternal `E:\backup-revioten` atau partisi `D:\backup-revioten`. Folder harus sudah ada: program sengaja tidak membuatnya, supaya backup tidak tertulis ke disk yang salah saat disk eksternal belum terpasang.
2. Tambahkan ke `.env`:
   ```
   BACKUP_DIR=E:/backup-revioten
   BACKUP_PASSPHRASE=<minimal 15 karakter>
   ```
   Simpan salinan passphrase di tempat lain (pengelola password, atau kertas di tempat aman). Tanpa passphrase, backup tidak bisa dibuka.
3. Nyalakan PostgreSQL (`docker compose up -d`), lalu dari folder repo: `go run ./cmd/revioten backup`.
4. Uji restore: `go run ./cmd/revioten restore -file E:/backup-revioten/revioten-<waktu>.dump.age`. Hasilnya database `revioten_restore`. Periksa isinya: `docker compose exec db psql -U revioten -d revioten_restore -c "select count(*) from customers"`.
5. Buang database uji setelah diperiksa: `docker compose exec db dropdb -U revioten revioten_restore`.
6. **Jadwal harian (Task Scheduler):** buat binary `go build -o bin/revioten.exe ./cmd/revioten`. Di Task Scheduler, buat task harian dengan Program `<folder repo>\bin\revioten.exe`, Arguments `backup`, dan Start in `<folder repo>` (tempat `.env` dan `compose.yaml`). Docker Desktop harus menyala pada jam itu. Periksa sesekali bahwa file baru muncul di folder backup.
7. **Enkripsi disk laptop** adalah langkah Anda sendiri, misalnya BitLocker di Windows Pro, dan mungkin butuh izin IT.
8. **Membuka backup tanpa aplikasi ini** (cadangan, belum dicoba): pasang alat `age` resmi, lalu `age -d -o revioten.dump revioten-<waktu>.dump.age` dan `pg_restore -d <database> revioten.dump`.

## 3. Bukti (container cloud, 30 Oktober 2026)

`BACKUP_DIR` diarahkan ke folder di luar repo (pengganti disk lain).

```

$ ./bin/revioten restore -file .../revioten-20261030-133947.dump.age

Rantai audit utuh: 2 entri. Ujung rantai yang dicatat manifest (entri 2) cocok.
```

Server lalu dijalankan di atas database hasil restore (`POSTGRES_DB=revioten_restore`, port 8095); `/health` menjawab `{"database":"ok","status":"ok"}`.

## 4. Konsep yang dipelajari

- **Backup yang belum pernah dipulihkan belum terbukti.** Karena itu kriteria selesainya restore, bukan backup.
- **pg_dump format custom** menyimpan isi database beserta skema, GRANT, trigger, dan tabel versi migrasi goose, sehingga database hasil restore langsung dikenali server. Role (`revioten_app`) tidak ikut, karena role milik seluruh server PostgreSQL, bukan satu database; restore menyiapkannya sendiri.
- **Enkripsi dan hash punya tugas berbeda.** Enkripsi (age: scrypt untuk passphrase, ChaCha20-Poly1305 untuk isi) menjaga kerahasiaan bila disk backup hilang. Hash SHA-256 di manifest membuktikan file tidak berubah sejak dibuat.
- **Tulis ke file sementara, lalu ganti nama.** Rename di folder yang sama berlangsung sekaligus, jadi file backup tidak pernah terlihat setengah jadi.
- **Restore dalam satu transaksi** (`--single-transaction`): gagal di tengah berarti tidak ada yang tersimpan.
- **Jangkar luar rantai audit:** hash ujung rantai yang disimpan di luar database tidak bisa ikut diubah oleh orang yang menulis ulang tabel audit.

## 5. Keputusan beserta alasannya

1. **age, bukan enkripsi buatan sendiri, gpg, atau openssl.** age adalah format standar dengan pustaka Go dan alat CLI resmi, jadi backup bisa dibuka tanpa aplikasi ini. gpg dan openssl harus dipasang terpisah di Windows, dan enkripsi buatan sendiri mudah salah.
2. **Passphrase, bukan pasangan kunci.** Lebih mudah dipahami dan dipulihkan di komputer lain. Ancaman yang dijaga adalah disk backup yang hilang; laptop sendiri dijaga enkripsi disk.
3. **`docker compose exec`, bukan `pg_dump` di Windows.** pg_dump di dalam container selalu sama versinya dengan server (18.6), dan tidak perlu dipasang.
4. **Restore selalu ke database baru.** Data yang sedang dipakai tidak bisa tertimpa karena salah ketik.
5. **Manifest tidak dienkripsi.** Isinya tidak rahasia, dan harus bisa dibaca untuk memeriksa file sebelum passphrase dimasukkan.

## 9. Latihan tulis tangan (tanpa AI)

Tulis perintah `revioten verify-backup -file <backup>` yang **tidak** memulihkan apa pun: ia membaca manifest, memanggil `backup.VerifyFile`, lalu mencoba membuka file dengan `backup.Decrypt` dan membaca isinya sampai habis (`io.Copy(io.Discard, r)`).

Kriteria lulus:
1. File utuh dengan passphrase benar: keluar tanpa error dan menulis tanggal backup serta ujung rantai audit dari manifest.
2. File yang diubah satu byte: ditolak sebelum passphrase dipakai.
3. Passphrase salah: ditolak dengan pesan yang tidak memuat passphrase.
4. Satu test Go dengan `t.TempDir()` dan `fakeDumper` (lihat `internal/backup/backup_test.go`) yang membuktikan ketiga hal di atas.
