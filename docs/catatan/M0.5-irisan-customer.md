Tujuan M0.5: satu irisan lengkap dari database sampai layar untuk customer. Isinya migrasi goose, query sqlc, API daftar dan tambah customer, dan layar daftar. Selesai bila customer yang ditambah di layar tersimpan dan test lulus.

## 2. Cara mengulang dari nol (Windows)

Dari root repo, di PowerShell. Semua perintah di bawah belum dicoba di komputer pemilik.

1. Ambil perubahan: `git pull`.
2. Nyalakan PostgreSQL: `docker compose up -d`, lalu `docker compose ps` sampai `healthy`. File `.env` dari M0.1 tetap dipakai.
   - Bila Docker berjalan di dalam WSL 2 (tanpa Docker Desktop), jalankan juga perintah `go` dan `npm` di dalam WSL 2, supaya testcontainers dan skrip E2E bisa memanggil Docker.
3. Test Go: `go test ./...`. Docker harus berjalan, karena test database menyalakan container sendiri.
4. Paket frontend berubah, jadi pasang ulang: `npm --prefix web ci`.
5. Test frontend: `npm --prefix web test` dan `npm --prefix web run check`.
6. Coba sendiri:
   - `npm --prefix web run build`, lalu `go run ./cmd/revioten`;
   - buka http://127.0.0.1:8080/customers, tambah customer `ab` dengan nama bebas, lalu muat ulang halaman;
   - coba `zz`, kode kosong, dan kode yang sama dua kali, lalu lihat pesannya.
7. Test E2E:
   - pasang browser sekali: `npm --prefix web exec -- playwright install chromium`;
   - lalu jalankan `npm --prefix web run test:e2e`.
8. Pastikan kode hasil generate sama dengan kontrak dan SQL:
   - jalankan `go generate ./...` dan `npm --prefix web run gen:api`;
   - lalu `git status`, yang seharusnya tidak menunjukkan perubahan;
   - di Windows, sqlc memakai parser WebAssembly (lihat `docs/versions.md`). Bila hasilnya berbeda dari yang di-commit, catat sebagai temuan.

## 4. Konsep yang dipelajari

**Kontrak dulu (contract-first).** `api/openapi.yaml` adalah satu-satunya tempat bentuk API ditulis. Server Go dan tipe TypeScript dibuat dari file itu. Bila kontrak berubah, kode yang tidak cocok langsung gagal dikompilasi, di Go maupun di TypeScript. Ini yang membuat layar web dan aplikasi lain nanti bisa memakai API yang sama (D-61).

**Kode hasil generate.** File berakhiran `.gen.go` dan `customers.sql.go` diawali `// Code generated ... DO NOT EDIT.` Kode itu tidak diedit tangan: ubah sumbernya (kontrak atau SQL), lalu jalankan `go generate ./...`. Baris `//go:generate go run modul@versi` menjalankan alat dengan versi tepat tanpa memasukkannya ke `go.mod`, sehingga dependensi alat tidak bercampur dengan dependensi program. Kode hasil generate tetap di-commit, supaya `go build` tidak butuh generator.

**Migrasi.** Setiap perubahan skema adalah satu file bernomor (`00001_...sql`) dengan bagian `-- +goose Up` dan `-- +goose Down`. goose mencatat migrasi yang sudah jalan di tabel `goose_db_version`, jadi `Migrate` aman dipanggil setiap program mulai. File migrasi dimasukkan ke binary dengan `go:embed`.

**sqlc.** Query ditulis dalam SQL biasa dengan nama (`-- name: ListCustomers :many`). sqlc membaca skema dari file migrasi, memeriksa query terhadap skema itu, lalu membuat fungsi Go bertipe. Kesalahan nama kolom ketahuan saat generate, bukan saat program berjalan.

**Tiga lapis tipe.** `db.Customer` (baris database, dari sqlc), `customer.Customer` (domain), dan `server.Customer` (kontrak API, dari oapi-codegen). Perubahan di satu lapis tidak otomatis bocor ke lapis lain, dan fungsi penerjemah (`fromRow`, `toAPICustomer`) menunjukkan dengan jelas di mana datanya berpindah.

**Strict server.** Handler menerima objek permintaan bertipe dan mengembalikan objek jawaban bertipe, misalnya `CreateCustomer422JSONResponse`. Status dan bentuk JSON-nya sudah ditentukan kontrak, jadi handler tidak bisa salah menulis status. Handler error bawaannya menulis `err.Error()` ke pengguna. Itu melanggar E-18, jadi diganti dengan `requestError` dan `responseError`, dan test `TestAPIErrorFormat` serta `TestAPIErrorHidesDetails` membuktikannya.

**Request ID dan context.** Middleware `withRequestID` menaruh ID di `context.Context` permintaan. Setiap error API dan setiap baris log memakai ID itu, sehingga laporan pengguna ("request ID T54B...") bisa dicocokkan dengan satu baris log. ID dari klien hanya dipakai bila bentuknya wajar, supaya tidak bisa menyisipkan baris log palsu.

**Pola route ServeMux Go 1.22.** Dua pola bentrok bila tidak ada yang lebih spesifik. `GET /` dan `/api/` ditolak saat didaftarkan (panic), karena untuk `GET /api/x` yang satu lebih sempit di method dan yang lain lebih sempit di path. Solusinya: halaman web didaftarkan sebagai `/` tanpa method, dan `handleSPA` sendiri menolak method selain GET dan HEAD. Untuk 404 dan 405 di API, `routeAPI` bertanya ke mux API lewat `apiMux.Handler(r)`, lalu menulis error JSON sendiri, bukan teks polos bawaan ServeMux.

**Batasan database sebagai penjaga terakhir.** Kode ganda tidak dicek dengan `SELECT` lebih dulu: dua permintaan bersamaan bisa sama-sama lolos cek itu. Batasan `UNIQUE` di database yang menolak, dan `IsUniqueViolation` menerjemahkan penolakan itu menjadi `ConflictError` (409). Aturan format juga ada di database (`CHECK`), sebagai pengaman bila nanti ada kode lain yang menulis langsung.

**Database template untuk test.** `dbtest.Main` menyalakan satu container per paket dan menjalankan migrasi sekali di database template. Setiap test mendapat database baru lewat `CREATE DATABASE ... TEMPLATE`, yang selesai dalam puluhan milidetik. Test tidak saling mengganggu, dan tidak perlu membersihkan data.

**Svelte 5: formulir.** `bind:value` menghubungkan input dengan variabel `$state`. `onsubmit={save}` dengan `event.preventDefault()` mencegah browser memuat ulang halaman. Tipe `ApiResult` (`ok: true` atau `ok: false`) memaksa kode layar menangani keberhasilan dan kegagalan.

**Test E2E.** Playwright membuka browser sungguhan, mengisi formulir, dan memeriksa tabel, lalu memuat ulang halaman untuk membuktikan data datang dari database. Skrip `web/e2e/server.mjs` membuat ulang database `revioten_e2e` setiap kali, jadi hasilnya tidak bergantung pada data development.

## 5. Keputusan beserta alasannya

1. **Generator Go lewat `go run modul@versi`, bukan `go get -tool`.** Diukur di salinan repo: `go get -tool` untuk oapi-codegen dan sqlc menambah sekitar 54 baris ke `go.mod` dan menaikkan beberapa modul tidak langsung milik program (misalnya grpc 1.67 ke 1.80). Dengan `go run`, `go.mod` program tetap bersih dan versi alat tetap terkunci di baris `go:generate`.
2. **Q-47: @hey-api/openapi-ts 0.99.0, plugin tipe saja.** Hanya kandidat ini yang lolos R-VER-03 (lihat `docs/evaluasi-desain.md`). SDK bawaannya tidak dipakai. Pemanggilan fetch ditulis tangan (sekitar 60 baris) supaya bisa dibaca dan dibangun ulang tanpa AI (D-12). Ini dipakai sementara sampai pemilik memutuskan Q-47.
3. **Status 422 untuk input salah, 400 untuk body yang tidak bisa dibaca, 409 untuk bentrok data** (ASUMSI E-20). Dengan begitu klien bisa membedakan "isi formulir salah" dari "permintaan rusak".
4. **Pesan per field memakai kode, bukan teks.** `details[].code` (misalnya `taken`) diterjemahkan layar lewat katalog teks, sehingga peralihan ke bahasa Indonesia tidak bergantung pada pesan Inggris dari server.
5. **Migrasi berjalan otomatis saat server mulai.** Cara paling sederhana untuk demo localhost (D-36). Di M1.3, migrasi dan program akan memakai role database yang berbeda (E-06), dan bagian ini disesuaikan.
6. **Konfigurasi membaca `.env` dengan aturan Docker Compose.** Server dan Compose membaca file yang sama, jadi password cukup ditulis sekali. Nilai di environment menang atas file. Hal ini dipakai test E2E untuk mengganti nama database tanpa menyentuh `.env`.
7. **Folder baru `internal/db/dbtest/` dan `web/e2e/`** dicatat di CLAUDE.md sebagai usulan, karena belum ada di struktur yang disetujui.
8. **`@types/node` 24.19.2**, bukan dist-tag `latest` (26.6.5), supaya tipe Node sama dengan Node yang dipakai (24 LTS).

## 6. Asumsi

- ASUMSI E-20: tabel kode error, bentuk `details`, aturan `X-Request-Id`, snake_case, dan batas body 1 MiB (rincian di `docs/evaluasi-desain.md`).
- ASUMSI E-21: nama customer wajib, 1 sampai 200 karakter, satu baris, dan boleh ganda.
- ASUMSI E-12: kode ZZ ditolak untuk customer karena dipakai untuk dokumen General/Common.
- Teks `description` di kontrak dan `message` di error berbahasa Inggris, sama dengan layar (Q-14).
- Contoh di kontrak dan test memakai nama fiktif ("Example Customer", kode AB), bukan customer asli (CLAUDE.md bagian 7).

## 9. Latihan tulis tangan (tanpa AI)

**Tugas: tambah satu endpoint dengan alur yang sama.** Tambahkan `GET /api/v1/customers/{code}` yang mengembalikan satu customer menurut kodenya.
1. Kontrak dulu: tambahkan path dengan parameter `code`, jawaban 200 (`Customer`) dan 404 (`Error` dengan code `not_found`).
2. Jalankan `go generate ./...`, lalu baca method baru di `StrictServerInterface` yang harus Anda isi.
3. Tambah query `GetCustomerByCode :one` di `sql/queries/customers.sql`, lalu `go generate ./...` lagi.
4. Tulis test dulu: `internal/customer` (kode ada, kode tidak ada, kode " ab " dirapikan) dan `internal/server` (200, 404 dengan format error yang benar).
5. Tulis `Service.Get` dan handler-nya sampai test lulus.

**Kriteria lulus.**
- `go test ./...` lulus, dan `go generate ./...` tidak mengubah file apa pun setelah Anda selesai.
- `curl -i http://127.0.0.1:8080/api/v1/customers/AB` menjawab 200, sedangkan `.../customers/XY` menjawab 404 dengan `"code":"not_found"` dan request ID yang sama dengan header.
- Tidak ada `err.Error()` yang sampai ke jawaban HTTP.

**Pertanyaan yang dijawab dengan tulisan sendiri** (2 sampai 3 kalimat per pertanyaan):
1. Kenapa kode ganda tidak dicek dengan `SELECT` sebelum `INSERT`?
2. Apa bedanya `db.Customer`, `customer.Customer`, dan `server.Customer`, dan kenapa tidak dipakai satu struct saja?
3. Kenapa test HTTP memakai `fakeCustomers`, sedangkan test `internal/customer` memakai database sungguhan?
