## 2. Cara mengulang dari nol (Windows)

Dari root repo, di PowerShell. Semua perintah di bawah belum dicoba di komputer pemilik.

1. `git pull`, lalu `docker compose up -d`.
2. `go test ./...` (Docker harus berjalan), lalu `npm --prefix web test` dan `npm --prefix web run check`. Paket npm tidak berubah di M1.2, jadi `npm --prefix web ci` hanya perlu bila belum pernah dijalankan.
3. `npm --prefix web run build`, lalu `go run ./cmd/revioten`. Migrasi `00003_create_roles.sql` berjalan sendiri, dan akun admin yang dibuat di M1.1 mendapat peran Admin.
4. Login dengan akun admin. Menu "Accounts" muncul. Buka menu itu, lalu buat akun kerja:
   - pilih "New person", isi nama contoh dan nama login;
   - centang "Author", lalu pilih "Own project group";
   - tekan "Create account". Password sementara tampil satu kali. Salin password itu.
5. Logout, lalu login dengan akun baru dan password sementara:
   - Anda langsung dibawa ke halaman ganti password;
   - setelah password diganti, menu "Accounts" tidak ada, dan halaman Customers tidak punya formulir "Add a customer".
6. Coba lewati layar: dengan akun baru, kirim `POST /api/v1/customers` lewat curl (langkahnya di CLAUDE.md, baris "Coba API dengan login"). Jawabannya 403 `forbidden`.
7. Kembali sebagai admin: ubah peran akun tadi, nonaktifkan lalu aktifkan lagi, dan reset password-nya. Baris akun admin Anda sendiri tidak punya tombol reset dan nonaktifkan.
8. Test E2E: `npm --prefix web run test:e2e`.

## 4. Konsep yang dipelajari

**Satu titik pemeriksaan, tolak bila tidak disebut.** Setiap operasi domain memanggil `Authorize(aktor, hak, resource)` sebelum melakukan apa pun. Fungsi ini menjawab `nil` hanya bila salah satu peran aktor punya hak itu. Selain itu jawabannya `ErrForbidden`, termasuk untuk aktor kosong dan hak yang tidak dikenal. Jadi kesalahan pemrograman (lupa mengisi aktor) berakhir dengan penolakan, bukan dengan akses.

**Pemeriksaan di layanan domain, bukan di HTTP.** `Authorize` dipanggil di `internal/customer`, `internal/auth`, dan `internal/access`, bukan di handler HTTP. Aturan bisnis tinggal di domain (R-API-01). Nanti service account dan API integrasi (M8.1, Tahap 9) memakai layanan yang sama, sehingga pemeriksaan izinnya ikut terbawa tanpa ditulis ulang.

**Peran sebagai data (RBAC).** Katalog hak (L-1 sampai A-4) tetap, karena kode memeriksa hak, bukan nama peran. Peran hanyalah baris di tabel `roles`, dan isinya baris di `role_permissions`. Menambah hak ke sebuah peran cukup mengubah data, tanpa mengubah kode (U3 bagian 5). Hak dibaca dari database setiap kali diperiksa, jadi perubahan peran langsung berlaku, juga untuk sesi yang sedang berjalan.

**Hak dasar tanpa diberikan.** Semua akun aktif memegang hak peran Viewer (L-1 sampai L-3) tanpa baris di `account_roles` (U3 bagian 1). Query `ListGrants` menggabungkan peran yang diberikan dengan peran Viewer memakai `UNION`. Akun yang dinonaktifkan tidak memegang hak apa pun.

**Cakupan dan resource.** Peran Penyusun dan Verifikator bisa dibatasi ke Project Group sendiri (D-71). Operasi yang menyentuh satu customer mengirim `Resource{CustomerID}`. Data Project Group dan pemegang jabatan baru ada di M1.4 dan M1.8, jadi sampai itu peran bercakupan Project Group tidak berlaku untuk customer mana pun (ASUMSI E-04). Bila data belum ada, jawaban paling aman adalah "tidak".

**Layar menyembunyikan, server menolak.** `GET /api/v1/session` mengirim daftar hak pengguna. Layar memakai `can('A-2')` untuk menyembunyikan menu dan tombol yang pasti ditolak. Ini hanya kenyamanan. Test E2E pertama membuktikan pengamannya ada di server: permintaan `fetch` langsung dari browser milik penyusun tetap dijawab 403.

**Test yang menelusuri kontrak, dan uji mutasi.** `TestPermissionsPerOperation` menjalankan setiap operasi di `api/openapi.yaml` dengan dua akun sungguhan: akun tanpa peran dan akun admin. Bagian `checkCoversContract` gagal bila ada operasi di kontrak yang belum masuk tabel test, sehingga endpoint baru tidak bisa lupa diuji. Untuk membuktikan test ini berguna, satu panggilan `Authorize` sempat dihapus sementara dari kode (uji mutasi), dan test langsung gagal.

**Balapan yang dipaksa terjadi.** Dua admin yang saling menonaktifkan pada saat bersamaan bisa sama-sama melihat "masih ada dua admin aktif", lalu keduanya berhasil, sehingga tidak ada admin tersisa. Kunci advisory (dari M1.1) membuat keduanya antre. Versi pertama test konkurensi ternyata tetap lulus tanpa kunci, karena kedua permintaan kebetulan tidak pernah bertumpuk. Karena itu ditambahkan kait test `afterAdminCount` yang menahan permintaan pertama tepat setelah menghitung admin. Dengan kait itu, test gagal tanpa kunci dan lulus dengan kunci.

**Bandingkan ID dari database, bukan teks dari klien.** Saat meninjau ulang kode ditemukan celah: "tidak boleh menonaktifkan akun sendiri" membandingkan teks ID dari URL dengan ID akun pemanggil. UUID yang sama dalam huruf besar (`01A180ED-...`) menunjuk akun yang sama di PostgreSQL, tapi lolos dari perbandingan teks. Perbaikannya: baca akun dulu, lalu bandingkan ID dari database. Test-nya ditulis dulu dan gagal, lalu lulus setelah perbaikan.

**Svelte: `$bindable` dan `bind:group`.** `RoleEditor` menerima `grants` lewat `$bindable()`. Induk menulis `<RoleEditor {roles} bind:grants />`, sehingga perubahan di dalam komponen langsung mengubah variabel milik induk. Komponen yang sama dipakai di formulir akun baru dan di baris tabel saat peran diubah. Tombol radio memakai `bind:group={kind}`: nilai radio yang dipilih masuk ke satu variabel.

## 5. Keputusan beserta alasannya

1. **Delapan peran U3 dan katalog hak sebagai data awal** (E-01, diputuskan). Peran approver tidak dibuat, karena approver memakai Viewer (D-70). Layar untuk mengubah isi peran menunggu M8.1 (D-66).
2. **Peran akun admin tidak bisa diubah sama sekali.** Ini cara paling sederhana untuk menjamin akun admin hanya memegang peran Admin (D-72) dan tidak kehilangan peran itu (D-73). Akun kerja tidak pernah bisa diberi peran Admin atau Viewer.
3. **Akun admin aktif terakhir tidak bisa dinonaktifkan**, dan tidak ada operasi hapus akun (ASUMSI E-26).
4. **Akun sendiri tidak bisa di-reset atau dinonaktifkan dari layar admin.** Password sendiri diganti lewat halaman ganti password, yang meminta password lama.
5. **Password sementara 26 karakter acak** (`crypto/rand.Text`), tampil satu kali di layar admin, dan wajib diganti saat login pertama (E-08). Server tidak menyimpannya, hanya hash-nya.
6. **Satu orang bisa punya akun kerja dan akun admin** (D-72). Formulir akun punya pilihan "Existing person" untuk membuat akun admin bagi orang yang sudah punya akun kerja.
7. **Daftar customer memakai hak L-2** (ASUMSI E-24), sedangkan menambah customer memakai A-2 (E-10).
8. **Mengurus akun sendiri lewat `Authorize` dengan aturan tetap** (ASUMSI E-25), supaya tidak ada operasi yang melewati titik pemeriksaan.
9. **Aksi yang mengakhiri sesi orang lain minta konfirmasi** (reset password, nonaktifkan) memakai `confirm()` bawaan browser, supaya kodenya tetap pendek.
10. **Peristiwa pengelolaan akun dicatat di log server** (akun dibuat, peran diubah, password direset, akun dinonaktifkan atau diaktifkan, akses ditolak). Di M1.3 peristiwa ini masuk audit log.
